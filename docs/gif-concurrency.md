# GIF 并发评估（阶段 4）

## 决策

保留生产代码串行转换，暂不增加“并发 2”。主机独立 FFmpeg 进程的吞吐量有提升，但同时运行两个高清任务的总 RSS 接近翻倍；Android FFmpegKit 的内存预算、设备性能和共享写入安全仍未验证。不能把主机结果直接当作手机上的收益。

## 复现

要求 Linux、Python 3、Pillow、psutil、FFmpeg/ffprobe。先使用阶段 3 工具生成素材或提供实际 WebM，再运行：

```sh
python tools/benchmark_gif_concurrency.py \
  --samples /tmp/gif-experiment/flat.webm /tmp/gif-experiment/gradient.webm /tmp/gif-experiment/alpha.webm \
  --output /tmp/gif-concurrency
```

输出目录必须不存在。每个输入转换两次，每批 6 个任务。普通/高清使用 App 当前参数，每种模式分别限制同时运行 1/2 个独立 FFmpeg 子进程。第一轮预热不计，之后重复 3 次，交替运行顺序。

测量墙钟时间、所有已退出子进程的 CPU 秒，以及每 10ms 采样所有活跃 FFmpeg 进程 RSS 的总和峰值。CPU 秒/墙钟秒表示平均占用的 CPU 核数，不是单核百分比。RSS 是采样值，可能漏掉短时峰值；共享页也可能被重复计算，不能当成设备总物理内存增量。采样不包含 Python 控制进程。

FFmpeg 内部线程设置保持默认，因此“并发 2”不是“最多用两个 CPU 线程”。每个任务输出独立文件名，SHA-256、GIF 帧数、时长、尺寸和透明像素检查均在计时之外。输出必须逐字节等于串行参考，否则工具失败。这里排除了 App 增量缓存命中：测的是每次确实需要转换的工作量，且 OS 文件缓存经过预热。

## 本次条件与结果

Linux x86_64 云主机，FFmpeg 7.1.5；沿用阶段 3 的三个合成 512×512、30 fps、3 秒 VP9 文件，各两次。不是实际贴纸语料，不是 Android 基准。透明和时长限制与阶段 3 相同；输出一致只说明并发没有引入额外差异，不代表原输出质量正确。

| 模式 | 并发 | 批次中位耗时（秒） | CPU 中位（秒） | 平均核数中位 | 最大采样 RSS（MiB） |
| --- | ---: | ---: | ---: | ---: | ---: |
| normal | 1 | 0.812 | 1.582 | 1.97 | 45.1 |
| normal | 2 | 0.600 | 1.843 | 3.31 | 90.0 |
| high | 1 | 7.099 | 7.790 | 1.10 | 152.1 |
| high | 2 | 4.039 | 7.982 | 1.98 | 293.0 |

本次普通批次耗时降低约 26%，高清约 43%；总 RSS 接近翻倍。所有 96 个输出（包括预热批次）与相应串行参考 SHA-256 一致，没有测试混合 PNG/GIF、损坏文件、取消或不同输入并发写同一输出。

## 共享状态与重叠写入审查

当前每个包内部按顺序运行，不能简单把 `for` 换成两个工作线程：

- `failCount`/`failReasons`、进度以及 `StickerFileIndex` 的可变集合都假设单线程访问。并发时必须由单一协调者归并结果，完成数不能沿用任务下标。
- 相同贴纸 ID 的 high/low 文件具有选择和删除依赖，必须作为一个串行工作单元；不能只锁单次 Map 更新。
- 输出文件与缓存 receipt 分别原子发布，但两步合起来不是事务。共享目标若允许 A/B 交错：A 发布普通输出，B 覆盖高清输出，A 再为普通 recipe 记录当前文件指纹，就可能把高清内容认作普通 recipe 的缓存命中。临时 JVM 检查直接调用实际 `StickerConversionCache` 并按此顺序操作，复现了该条件。这个确定性交错验证说明并发准入条件，不证明当前 UI 能直接触发重复同步。
- 必须以包目录或完整输出路径为键，将检查缓存、转换、发布、清理、记录凭证纳入同一排他范围；同一个 ID 的相关输出还需共同协调。仅限制工作线程数量不能防止两个入口同步同一包。
- 删除/清缓存、源文件导出、Activity 生命周期和完成回调也需验证。工作池应全局有界，避免每个包各建两个线程导致总体并发失控。

## 后续准入条件

先完成上述共享目标的排他与结果归并设计，并验证重复请求、失败恢复、取消/生命周期、同 ID 高低清、并行删除等场景；再用真实 Android 设备和贴纸包比较串行/并发 2 的吞吐、峰值内存、低内存行为和温控。明确设备预算后，才考虑有回退的全局并发上限。此次未新增线程池、未修改 App、未更换 FFmpeg 依赖或参数。
