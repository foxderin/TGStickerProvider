# GIF 参数评估（阶段 3）

> 历史阶段记录：后续经用户批准的8任务上限、libvpx/APNG及新配方实现见 [parallel-conversion.md](parallel-conversion.md)。本页保留当时的测量和决策，不代表当前生产配置。

## 结论

暂不修改 App 的普通/高清参数，也不增加新的质量开关。先交付可复用的参数实验工具，避免把主机上的速度优势当作 Android 性能，或为了加速悄悄牺牲透明度。

候选流程 `fps -> scale -> palettegen -> paletteuse` 的工作量小于当前全尺寸/全帧率高清流程，但这也是分辨率和帧率的取舍，不是“无损优化”。在当前合成样本上，它比普通档更慢且输出更大。没有真实贴纸语料和 Android 设备验证，不足以确定一个适合默认使用的均衡档。

## 复现

开发工具不参与 App 构建。要求 Python 3、Pillow、FFmpeg/ffprobe，并且 FFmpeg 包含 `libvpx`/`libvpx-vp9` 解码器和 `libvpx-vp9` 编码器。

```sh
# 目录必须不存在；生成 3 个合成 WebM，先预热一次，再各测 3 次。
python tools/benchmark_gif.py --output /tmp/gif-experiment

# 也可以使用自己的 VP8/VP9 WebM；文件路径带空格也支持。
python tools/benchmark_gif.py --output /tmp/gif-real --samples sticker1.webm sticker2.webm
```

输出包括 GIF、JSON 中的每次耗时/中位数、字节数、帧数、时长、每帧透明像素数量范围、源文件 SHA-256 和 ffprobe 元数据。默认生成样本时，还会保留源 PNG 帧以便核对。输出只写到指定的新目录，不改动原文件。

计时覆盖进程启动、解码、滤镜、编码和文件写入，排除样本生成和输出检查。各轮交错参数顺序，第一轮预热不计入中位数。不固定 CPU 频率、核心数量或系统负载，不能当成严格性能基准。透明像素数量只能发现明显丢失，不能代表边缘、颜色或观感质量合格。

## 参数

| 模式 | 流程 | 作用 |
| --- | --- | --- |
| 当前普通 | `scale=320:-1`，输出 `-r 10` | 保持现有 App 参数 |
| 当前高清 | `split[v],palettegen,[v]paletteuse` | 保持现有 App 参数 |
| 实验候选 | `fps=15,scale='min(320,iw)':-1:flags=lanczos,split[a][b];[a]palettegen[p];[b][p]paletteuse=dither=bayer:bayer_scale=3` | 先减帧/缩放，再生成调色板；不放大小图；Bayer 有序抖动 |

工具分别运行自动解码与显式 libvpx 解码，用来区分解码阶段丢失 alpha 和 GIF 转换阶段的问题。显式解码仅用于诊断，不是已获 Android 验证的生产方案。

## 本次测量条件

- Linux x86_64 云主机，FFmpeg `7.1.5-0+deb13u1`，Pillow 13.0.0。
- 三个自行生成的 512×512、30 fps、3 秒 VP9 WebM：不透明平色移动图形、不透明渐变背景、透明背景带半透明边缘的移动图形。
- 素材简单，不能代表真实 Telegram 贴纸。没有测 Android、Xposed 流程、峰值内存、电量或设备发热。
- App 依赖仍是 `io.github.maitrungduc1410:ffmpeg-kit-min:6.0.1`，与主机 FFmpeg 的版本/配置不同。

### 主机结果（自动解码；中位数秒 / KiB）

| 合成样本 | 普通 | 高清 | 候选 |
| --- | ---: | ---: | ---: |
| flat | 0.116 / 63.3 | 0.907 / 215.9 | 0.163 / 161.4 |
| gradient | 0.132 / 93.6 | 1.928 / 3226.7 | 0.403 / 115.8 |
| alpha | 0.133 / 55.1 | 0.758 / 231.3 | 0.228 / 160.3 |

所有普通输出为 320×320，实测 32 帧/3.2 秒；高清为 512×512、90 帧/3 秒；候选为 320×320、45 帧/3 秒。普通的输出侧 `-r` 在这组主机样本中改变了时长，进一步说明应验证时间轴而不是只比较文件大小。

### 透明度诊断

透明样本的自动解码结果：三个模式每帧的透明像素数均为 0。显式 `libvpx-vp9` 后：

- 普通仍为 0，说明仅更换解码器不足以解决这条主机转换流程的透明问题。
- 高清每帧 241,823 个透明像素。
- 候选每帧 94,396–94,412 个透明像素（尺寸不同，数量不可直接与高清比较）。

GIF 不能保留连续半透明，调色板流程默认以 alpha 128 为阈值。这些结果不等于已验证所有透明边缘或没有色带；使用前仍需在浅色/深色背景查看动画。

当前下载的 Android min AAR 的 arm64 `libavcodec.so` 构建配置包含 `--disable-autodetect`，没有 `--enable-libvpx`。这不等于运行时能力验证，更不能据此断言 App 在真实设备上必然出现与主机相同的透明问题。不要直接在 App 中加入 `-c:v libvpx-vp9`：应先在目标设备确认解码器存在，以及依赖变更的体积、兼容性和许可影响。

## 下一步准入条件

1. 收集实际导出的 VP8/VP9 WebM，覆盖透明/不透明、渐变、细线文字、快速运动、小尺寸、非正方形和不同帧率；确认授权后再使用或分享，不把用户贴纸自动提交进仓库。
2. 在 App 当前 Android 依赖上记录解码器/编译配置，测试真实输出的透明背景、边缘和时间轴。
3. 分开评估解码器能力与质量参数；若要更换 FFmpeg 依赖，应作为独立阶段，不混入参数优化。
4. 在真实设备上记录耗时、内存、文件大小，人工复核浅/深背景观感后，才决定是否提供可选均衡档。
5. 若将来修改生产参数，同步更新转换缓存 recipe，避免旧输出被误认为新设置的结果。

参考：[FFmpeg palettegen/paletteuse 文档](https://ffmpeg.org/ffmpeg-filters.html#palettegen)、本机 `ffmpeg -h filter=paletteuse`。Android 构建验证通过不替代上述设备/画质验证。
